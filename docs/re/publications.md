## 1. Поисковая форма → `build_search_form(q)`

Форма `form[name=results]` на `querybox.asp`, отправка JS `query_message()` → `POST /query_results.asp`.
Порядок полей = **порядок в DOM** (так их отправляет `FormData`). Он отличается от порядка в таблице
`reverse-engineering.md` §3: чекбоксы «где искать» стоят в две колонки, и в DOM идут
`where_name, where_affiliation, where_abstract, where_fulltext, where_keywords`.

```
querybox_name="" authors_all="Петров В А|" titles_all="8610|" rubrics_all="500000|" changed=1 queryid=""
ftext=<текст> where_name where_affiliation where_abstract where_fulltext where_keywords where_references=""
type_article type_disser type_book type_report type_conf type_patent type_preprint type_grant type_dataset
search_itemboxid="" search_morph search_freetext search_fulltext search_open search_results
begin_year=0|год end_year=0|год issues=all|m1|m3|m6|m12 orderby=rank|date|insdate|name|title|cited
order=rev|nrm queryboxid=0 save_queryboxid=0
```

* Отмеченные чекбоксы отправляются со значением `on`, неотмеченные не отправляются вовсе.
* Пустые `select` `rubrics`/`authors`/`titles` (без выбранных option) браузер не отправляет; их значения
  JS кладёт в скрытые `*_all` через `|` с завершающим `|`. Имена авторов нормализуются: точки → пробелы
  (`Петров В.А.` → `Петров В А`), как в примере из RE-заметок (не проверено вживую).
* `search_itemboxid` — `select` с выбранным `<option value="">`, поэтому отправляется всегда (пустым).
* `onClick` у `where_fulltext` отмечает и все остальные «где искать»; `effective_where()` повторяет это.
* `changed=1` обязателен: без него сервер показывает последний запрос сессии.
* По умолчанию (как `clear_query()` на сайте): где — название, аннотация, ключевые слова; все 9 типов;
  `search_freetext` включён, морфология выключена; годы `0`; `issues=all`, `orderby=rank`, `order=rev`.
* Проверки (как в `query_message()`, сообщения по-русски): нет условий → «Не заданы условия поиска»;
  текст из 1 символа; текст без полей «где искать»; ни одного типа. Плюс `year_from <= year_to`.
* Страницы 2..N — `GET /query_results.asp?pagenum=N` в той же сессии (`page_params`). Сервер хранит
  последний запрос сессии: `qget_patent_p2` из черновиков RE (GET с другими параметрами, но без
  `changed=1`) вернул 2-ю страницу **предыдущего** запроса (290705 записей), а не патентов.
  `search_signature(q)` — sha256 (16 hex) от urlencode формы без номера страницы: клиент сравнивает его с
  подписью запроса, который сейчас «висит» в серверной сессии, и при совпадении листает `pagenum`.

## 2. Результаты поиска → `parse_search_results`

* Счётчик: текст `ВСЕГО НАЙДЕНО ПУБЛИКАЦИЙ: <font>290705</font> из <font>82293065</font>` → `total`,
  `total_in_database` (регулярка по тексту `body`).
* Строки: `table#restab tr#a<ID>` → `parsers.rows.parse_publication_rows` (раздел 3). 100 на странице.
* Пагинатор: `tr.menus` с ссылками `query_results.asp?pagenum=N`; текущая страница — ячейка
  `td[bgcolor=#5c6aa6]` без ссылки; последняя — ссылка «В конец» (`pagenum=2908`). Ссылка «Следующая
  страница» из правой панели «Возможные действия» тоже ведёт на `pagenum`, поэтому учитываются только
  строки с классом `menus` или с ≥ 2 разными номерами. Без пагинатора (одна страница) `pages =
  ceil(total/100)`, `page` — из аргумента.
* Пустой результат: счётчик `0`, или нет ни счётчика, ни таблицы, но есть «РЕЗУЛЬТАТЫ ПОИСКОВОГО
  ЗАПРОСА» / «ничего не найдено» / «не найдено ни одной…» → `total=0, items=[], pages=0`. Проверено на
  живой странице (`query_results_empty.html`, 13.10.2026): заголовок «РЕЗУЛЬТАТЫ ПОИСКОВОГО ЗАПРОСА»,
  пустой `<b></b>` вместо счётчика, таблицы `restab` нет, текст «Не найдено публикаций, соответствующих
  запросу» → `total=0, items=[], page=1, pages=0`, это не `ParseError`.
* Страница 2+ (`query_results_page2_graphene.html`, «графен», год ≥ 2023): счётчик «1051 из 82293065»
  есть на каждой странице; нумерация строк сквозная (101…200); текущая страница — ячейка
  `td[bgcolor=#5c6aa6]` с `<font>2</font>` без ссылки, последняя — «В конец» (`pagenum=11`). Номер
  страницы берётся из пагинатора, даже если вызывающий передал другой `page`.
* Капча → `CaptchaRequired`; страница без счётчика/таблицы и без признаков пустого результата →
  `ParseError`.

## 3. Строки публикаций (`parsers/rows.py`)

`<tr id="a<ID>">` (поиск) / `<tr id="arw<ID>">` (списки автора/организации, выпуск, оглавление книги):
1-я ячейка — номер (`1` или `87.`), ячейка со ссылкой `item.asp?id=` — название, авторы (`<i>` сразу
после названия), библиографическая строка; последняя ячейка — цитирования; если после основной ячейки
ещё две — средняя это страницы (содержание выпуска, оглавление).

Исправлено:

* **Авторы.** Раньше брался первый `<i>` ячейки. У глав и некоторых докладов авторов нет, а `<i>` стоит
  внутри источника («В книге: … <i>Мифтахова Р.Г.</i> Монография…»): глава получала чужого автора, а
  источник обрезался до «Монография. Уфа, 2024. С. 108.» (и тип становился `book`). Теперь `<i>` считается
  авторами, только если между названием и ним нет текста.
* **Пробелы в источнике.** `node.text(separator=" ")` давал «Журнал . 2024. № 5 . С. 1»; теперь текст
  склеивается как в разметке (пробел только у `<br>`/блоков): «Журнал. 2024. № 5. С. 1.».
* **Год патента** — дата сразу после номера (дата публикации), а не последний год строки (год заявки):
  «RU 2760636 C2, 29.11.2021. Заявка № … от 19.12.2018.» → 2021 (`row_year`).
* **Год и страницы** (живой тест 13.10.2026, `query_results_page2_graphene`). Год брался как последнее
  «годоподобное» число строки, и «Журнал физической химии. 2025. Т. 99. № 12. С. 1901-1909.» давал 1909.
  Теперь `source_year` (его вызывают `row_year`, `parse_reference_rows` и `ContainerRef.year` карточки)
  сначала вырезает страницы — «С. a-b», «C.», «P.», «pp.», «стр.» и объём книги «320 с.», — и только потом
  ищет последний год; если вне страниц года нет, остаётся прежнее правило.
* **Строка без авторов** бывает и в поиске (`83040860`, неподписанная статья): `<br>` после названия
  сразу переходит в источник, `authors=[]`, `source` полон.
* **Тип** (`infer_kind(source, *, journal_link=False, default=None)`), порядок правил: сначала структурные
  признаки — «В книге:» (chapter) → «В сборнике:» (conference, если есть признаки конференции, иначе
  chapter); затем, только если в строке **нет** ссылки на выпуск `contents.asp`, патент/свидетельство →
  диссертация/автореферат; → отчёт → депонированная рукопись/препринт → грант → набор данных → строка со
  ссылкой на выпуск `contents.asp` (article: так «Труды … конференции „Графикон“» с номером выпуска —
  журнал) → книга (монография, пособие, ISBN, сборник…, а также строка вида «Город, 2023.») →
  конференция по ключевым словам → журнальные признаки (№, Т., С.) → other.
  Шаблоны патента и диссертации **привязаны к началу строки**: настоящие строки всегда начинаются с типа
  («Патент на изобретение RU …», «Патент на полезную модель …», «Свидетельство о регистрации программы для
  ЭВМ …», «диссертация на соискание …», «автореферат диссертации …»). Раньше поиск шёл по всей строке и
  раньше структурных признаков, поэтому слова из названия журнала или книги меняли тип: статья журнала
  «Патенты и лицензии. Интеллектуальные права» (со ссылкой `contents.asp`) становилась `patent`,
  «В книге: Патентное право. Учебник…» — `patent`, «В сборнике: … диссертационные исследования … конференции»
  — `dissertation`, а экспорт строк без карточки (BibTeX/RIS/Zotero) получал тип патента/диссертации.
  Проверено на всех 811 строках фикстур: ни один тип не изменился.
* `parse_publication_rows(tree, *, default_kind=None)` — для строк без источника (содержание выпуска →
  журналам стоит передавать `"article"`, оглавление книги → `"chapter"`). Без аргумента поведение прежнее.
* **99 строк вместо 100 в `author_items_3771`** — не ошибка: строка 88 — `tr#brw1062348813`, публикация
  «из списков цитируемой литературы» (`show_refs=1`), без карточки и без ссылки `item.asp`. Такие строки
  пропускаются; новая функция `parse_reference_rows(tree) -> list[ReferenceHit]` возвращает их
  (`ref_id`, название в `<b>`, авторы, источник, год, цитирования, номер).
* **«Версии:»** (QA, 13.10.2026). У переведённых статей в ячейке названия вложена таблица
  `<td>Версии:</td><td><a href="item.asp?id=…">название, авторы, выходные данные версии</a></td>`. Раньше
  её текст попадал в `source` («… С. 1241-1258. Версии: ATLAS VS. TOTEM … С. 1152-1164.»), и экспорт
  брал страницы перевода. Теперь таблица исключается из `source`, а id версий кладутся в
  `PublicationHit.versions` (у них свои карточки). Ячейки строки берутся только прямые (`tr.iter()`),
  иначе вложенные `td` ломали определение колонки страниц; `journal_link` учитывает только ссылки
  самой записи.
* **Курсив в названии** (QA). «CRISPR-COPIES: AN <I>IN SILICO</I> PLATFORM…»: первый `<i>` ячейки был
  внутри названия, авторы терялись и попадали в `source`. Теперь авторы — первый `<i>`, текст которого
  начинается сразу после названия.

## 4. Карточка `item.asp` → `parse_publication`

Корень разбора — ячейка `td`, содержащая таблицу с `p.bigtext` (центральная колонка). Текст разбирается
так: узел превращается в «строки» (разрыв на `<br>`, блочных тегах, `td/tr` и на распорках
`<span style="margin-left:20px">`), строки — в поля «Метка: значение» (+ строки-продолжения без метки).

Метка, относящаяся к блоку книги/патента/диссертации, который не создан (например, «Тираж» у доклада),
уходит в `extra`.

`normalize_kind(type_raw, *, journal, container, conference)`: «статья в журнале - …» → article;
патент/свидетельство → patent; диссертация/автореферат → dissertation (`dissertation.is_autoreferat`);
глава → chapter; «сборник трудов конференции» → **proceedings**; тезисы/доклад/«…конференции» →
conference; «статья в сборнике статей» → chapter; отчёт → report; депонированная рукопись, препринт,
«статья в открытом архиве» → preprint; грант; набор данных → dataset; монография/пособие/сборник… →
book; если «Тип» нет — по наличию блоков ЖУРНАЛ/КОНФЕРЕНЦИЯ/ИСТОЧНИК.

Ошибки: капча → `CaptchaRequired`; нет ни `eLIBRARY ID:`, ни `p.bigtext` → `NotFound`, если в тексте
«публикация не найдена / не существует / удалена…» (**реальной такой страницы нет**, текст угадан),
иначе `ParseError`.

## 5. Полный текст

* `ispdf.asp?itemid=ID` → `parse_fulltext_flag`: `<a href="javascript:load_article(ID)"><img
  src="/images/download_green.png" title="Доступ к полному тексту открыт"></a>`. Цвет иконки → доступ
  (легенда списков): green «открыт» → `open`; blue «на сайте издателя / внешнем сайте» → `external`;
  yellow «через систему заказа» / «Можно приобрести … за 250 руб.» → `order` (+ `price_rub`); orange
  «закрыт» → `closed`; red (старый `pdf_red.gif`) → `paid` (по RE-заметкам, в легенде красного нет).
  Пустой фрагмент — полного текста нет. Фрагмент грузится лениво по одному на строку — не запрашивать без
  нужды (бюджет запросов).
* На карточке: патент — файл на eLIBRARY (`file_article(47430099, 1)`, зелёная иконка) → `available=True,
  access=open`; статья — «Приобрести за 455 руб.» → `paid`; диссертация — ссылка на dlib.rsl.ru →
  `external`; глава — «Добавить ссылку на полный текст» → `can_add_link`. Для анонима все JS-функции
  выдают «необходимо войти», прямого URL PDF на странице нет; если у вошедшего появится ссылка
  `*.pdf` / `full_text.asp` / `/download/`, она попадёт в `files[].url` (**не проверено**).

## 6. Не проверено / открытые вопросы

* Нет фикстур: аннотация, английская аннотация статьи, доклад с ИСТОЧНИК/КОНФЕРЕНЦИЯ, препринт, отчёт,
  грант, набор данных, сборник конференции с оглавлением, СПИСОК ЛИТЕРАТУРЫ, страница «публикация не
  найдена», вошедший пользователь. Желательно сохранить при живом тесте (`item_conf_41770713` получил
  капчу). Пустой результат поиска и страница 2 результатов сохранены 13.10.2026 (раздел 2).
* `item_article_54076582.html` (13.10.2026): статья без аннотации на карточке (`abstract=None`), с
  блоком «ОПИСАНИЕ НА АНГЛИЙСКОМ ЯЗЫКЕ» (название, авторы, аффилиации, без аннотации и ключевых слов),
